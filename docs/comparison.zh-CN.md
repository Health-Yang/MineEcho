# MineEcho 与常见 AI 助手方案对比

这份文档用于解释 MineEcho 的定位。它不是为了证明其他项目不好，而是帮助用户判断 MineEcho 适合解决什么问题。

## 总览

| 方案类型 | 典型优势 | 常见限制 | MineEcho 的侧重点 |
|----------|----------|----------|-------------------|
| 普通 AI Chat 客户端 | 上手快，适合即时问答 | 长期记忆弱，知识和工具分散 | 把聊天放进记忆、知识、skill、成本控制闭环 |
| RAG 知识库 | 适合查文档和问资料 | 行动能力弱，chunk 容易黑箱化 | Wiki++ 多层知识结构 + 图谱 + alignment |
| Agent 工具框架 | 能调用命令、工具、浏览器或 workflow | 输出噪声大，长期上下文成本高 | TokenLess 压缩工具输出，并把任务结果沉淀进记忆 |
| AI 应用平台 | 能管理多个 AI 应用入口 | 应用之间割裂，难共享用户上下文 | AI 应用转换成 skill，进入同一套路由和健康检查 |
| 企业知识中台 | 管理能力强，适合组织知识 | 个人长期习惯和本地私有运行较弱 | 本地优先、个人记忆优先，同时保留团队扩展空间 |

## 1. 相比普通 Chat UI

普通 Chat UI 的核心价值是“问答入口”。MineEcho 的核心价值是“长期助手循环”。

MineEcho 会把用户交互拆进 L0-L3 记忆树：

- L0：原始交互片段，用于近期精确召回。
- L1：日摘要，用于把当天任务和偏好压缩成可复用上下文。
- L2：周摘要，用于阶段性目标和主题沉淀。
- L3：月归档，用于长期趋势和人生总结类视图。

用户再次提问时，MineEcho 会基于关键词、语义、本地向量、重要度和时间新鲜度检索候选记忆，再把相关上下文注入回答链路。这样它不是简单保存历史，而是尝试在回答时“记起来”。

## 2. 相比单纯 RAG 知识库

很多 RAG 系统的核心结构是“文件切 chunk + embedding 检索”。这对问答有效，但长期维护时容易出现几个问题：

- 用户很难知道知识从哪里来。
- chunk 之间缺少结构关系。
- 文档更新后，知识版本和实体关系不容易管理。

MineEcho 的 Wiki++ 知识库采用多层结构：

- raw 原始层：保留导入来源。
- wiki 智能层：面向人和 AI 的高密度知识页。
- chunk 索引层：服务检索和引用。
- graph 图谱层：维护实体、关系和邻域。
- alignment 对齐层：把记忆和知识库候选关系交给用户确认。

查询时会融合向量搜索、BM25、结构化搜索和图谱通道，而不是只依赖向量相似度。

## 3. 相比 Agent 工具框架

Agent 工具框架通常强调“能做事”，例如执行命令、调用脚本、读写文件、运行 workflow。MineEcho 也希望支持行动能力，但更关注行动后的沉淀：

- 工具输出进入上下文前，先由 TokenLess 根据场景压缩。
- 排错、写代码、执行命令、写文档等任务会使用不同的输出保留策略。
- 关键任务结果可以进入记忆系统，后续再被召回。

这意味着 MineEcho 不只是“调用工具”，而是把工具调用变成长期助手经验的一部分。

## 4. 相比 AI 应用平台

很多 AI 应用平台会把 RAG 应用、workflow 应用、聊天应用做成多个入口。问题是用户需要自己判断打开哪个应用，应用之间也不一定共享上下文。

MineEcho 的做法是把 AI 应用转换为 skill：

- AI 应用注册后进入同一个 skill registry。
- 系统从 name、description 和 mode 生成触发依据。
- 用户提问时，路由器根据 trigger、name、description、mode evidence 打分。
- 设置页和技能中心可以查看健康状态、触发词和导入结果。

目标是让用户自然提问，由 MineEcho 判断是否应该调用某个 skill 或 AI 应用。

## 5. TokenLess 的差异

TokenLess 不是简单截断长文本，而是场景化上下文压缩层。

当前规则覆盖 git、npm、cargo、docker、文档抽取和通用长输出。它会优先保留：

- error、warn、failed、stack trace 等失败证据。
- pass/fail/skip 计数。
- 命令、退出码、工具名和场景信息。
- 头尾上下文和关键行。
- 文档结构标题和去重后的内容片段。

基于当前规则结构，常见长输出可估算节省约 20%-85% token。这个数字不是官方 benchmark，而是工程估算；MineEcho 会在本地记录 raw/reduced 字符数和 estimated tokens saved，后续可以基于真实工作负载补充 benchmark。

## 适合使用 MineEcho 的场景

- 你希望 AI 记住长期偏好、项目背景和历史任务。
- 你有一批资料，希望它们变成可维护的个人或团队知识库。
- 你需要把多个 skill、脚本或 AI 应用接入一个统一助手入口。
- 你关心长期使用 AI 时的上下文成本和输出噪声。
- 你倾向本地优先，模型 key、聊天历史、会议音频和运行数据尽量留在自己机器上。

## 不适合的场景

- 你只需要一个轻量聊天界面。
- 你只需要企业级权限、审计、SSO 和多租户管理。
- 你需要完全托管的 SaaS，不想自己部署本地服务。
- 你需要已经稳定商业化的成熟产品，而不是早期开源项目。
