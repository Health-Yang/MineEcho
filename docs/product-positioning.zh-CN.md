# MineEcho 产品定位与核心亮点

MineEcho 的定位不是“又一个聊天界面”，而是一个面向个人和小团队的本地优先 AI 助手底座。它把记忆、知识、技能和成本控制放在同一条链路里，让助手可以持续积累上下文、调用能力、复用知识，并控制长期运行成本。

一句话概括：

> MineEcho = 记住用户 + 学习知识 + 调用技能/AI 应用 + 用 TokenJuice 控制上下文成本。

## 1. 记-学-用-省：一个闭环，而不是四个孤立模块

| 环节 | MineEcho 做什么 | 用户价值 |
|------|-----------------|----------|
| 记 | 对话、会议、技能使用和知识交互进入记忆系统 | 助手能跨会话回忆用户说过什么、做过什么 |
| 学 | 外部文档进入 Wiki++ 知识库，并与知识图谱、记忆对齐 | 不只是上传文件 RAG，而是沉淀成可浏览、可检索、可复用的知识层 |
| 用 | Skill 和 AI 应用统一进入技能注册表，由路由器按用户意图推荐/调用 | AI 应用不再是孤岛，可以像 skill 一样参与工作流 |
| 省 | TokenJuice 对命令输出、文档抽取、日志和任务结果做规则压缩与指标统计 | 长上下文、工具调用和知识导入不再无限堆 token |

相比只做聊天、只做知识库或只做 Agent 工具链的产品，MineEcho 的重点是让这四件事互相增益：

- 记忆为聊天提供用户历史和偏好。
- 知识库为回答提供外部证据和结构化资料。
- Skill/AI 应用把“知道”变成“能做”。
- TokenJuice 把工具输出、文档抽取和长任务结果压缩成适合模型消费的上下文。

## 2. 记忆系统：从短期上下文到 L0-L3 长期记忆

MineEcho 目前同时包含两套互补记忆视角。

### 2.1 运行时记忆：Working / Short-term / Long-term

| 层级 | 作用 | 当前实现 |
|------|------|----------|
| Working Memory | 当前会话的近期上下文 | 保存最近消息、任务类型、相关技能和实体；会话结束后自然过期 |
| Short-term Memory | 当日交互、偏好、任务 | SQLite 持久化，记录 chat、skill invocation、preference、task 等事件 |
| Long-term Memory | 跨会话用户画像和长期洞察 | 记录工作风格、技术栈、领域偏好、技能使用模式和背景审查提取的 insight |

这套结构解决的是“用户今天和最近一段时间做过什么、喜欢什么、常用什么技能”。

### 2.2 Memory Tree：L0 / L1 / L2 / L3 分层压缩

| 层级 | 含义 | 默认粒度 | 价值 |
|------|------|----------|------|
| L0 | 原始记忆片段 | 对话、文档、skill、knowledge、meeting 产生的新内容 chunk | 保留细节，可追溯 |
| L1 | 日摘要 | 多个 L0 合并成每日摘要 | 把一天的碎片压成高密度记录 |
| L2 | 周摘要 | 多个 L1 合并成周摘要 | 支持跨天、跨主题回忆 |
| L3 | 月归档 | 多个 L2 合并成月度归档 | 支持长期成长和历史总结 |

默认参数体现了“先保细节，再逐层抽象”的策略：

- L0 chunk 上限约 3000 tokens。
- L0 累积到约 21000 tokens 可触发 L1 seal。
- L1 目标约 500 tokens。
- L2 目标约 800 tokens。
- L3 目标约 1000 tokens。

### 2.3 MineEcho 如何“记起来”

当用户提问时，MineEcho 会在聊天上下文构建阶段执行记忆召回：

1. 先取最近 L0 chunks，按关键词、中文语义别名、本地语义向量、重要性和时间衰减做粗排。
2. 对粗排前 30 条使用可用的 embedding provider 进行二次语义重排；如果外部 embedding 不可用，自动回退本地语义向量。
3. L1/L2 摘要会先经过本地语义门槛，再用 embedding 增强排序，避免无关摘要被高基线向量分数误召回。
4. 最终按 token budget 注入相关 L0、L1、L2 片段到模型上下文。

这意味着 MineEcho 不只是把历史堆进 prompt，而是用“近期细节 + 中期摘要 + 长期画像”的方式找回和当前问题相关的记忆。

## 3. Wiki++ 知识库：从 Karpathy 式高密度资料到可运行知识层

MineEcho 的知识库内部称为 Wiki++。它的设计目标接近 Karpathy 式“给模型高质量、高密度、结构清晰的知识”，但不是只维护一份人工整理文档，而是把导入资料变成可检索、可浏览、可图谱化的知识系统。

### 3.1 与普通 RAG 的差异

| 普通 RAG | MineEcho Wiki++ |
|----------|-----------------|
| 直接切 chunk 检索原文 | raw 原始层 + wiki 智能层双层存储 |
| 每次查询都让模型从碎片里重新理解 | 先把文档整理成 concepts/entities/sources/comparisons/syntheses |
| 检索结果多是孤立片段 | wiki 页面、frontmatter、标签和图谱关系可以互相引用 |
| 主要依赖向量相似度 | 向量 + BM25 + 结构化 + 图谱通道融合 |

### 3.2 知识库的分层

| 层 | 内容 | 作用 |
|----|------|------|
| raw/ 原始层 | 用户上传文件、URL 导入内容、原始抽取文本 | 保留证据源，不直接被覆盖 |
| wiki/ 智能层 | LLM 整理出的结构化 Markdown 页面 | 形成可读、可维护、可交叉引用的知识页面 |
| chunk 索引层 | 按 H2、段落、句子 fallback 切分的检索块 | 支持向量和 BM25 检索 |
| graph 图谱层 | 文档、概念、实体、标签、关系边 | 支持邻域解释和关联扩展 |
| alignment 对齐层 | 记忆与知识候选链接、提交历史 | 把用户旧记忆和外部知识连接起来 |

### 3.3 查询时的四通道检索

用户调用知识库时，MineEcho 当前使用四通道混合检索：

1. **向量搜索**：通过 embedding 找语义相似 chunk。
2. **BM25 搜索**：通过中文 n-gram 和英文 token 找关键词命中。
3. **结构化搜索**：利用 title、type、tags、heading 等 wiki 元数据。
4. **图谱通道**：先匹配实体节点，再走一跳/轻量二跳邻域，找到关键词不完全匹配但关系相关的文档。

四个通道的结果通过 RRF 融合，避免单一向量或关键词通道误判。

## 4. Skill 与 AI 应用：把能力接进同一个工作台

MineEcho 不把 AI 应用当成单独入口，而是把它们转换成“skill-like callable units”。

### 4.1 导入与注册

- 原生 skill 可以通过 JSON、ZIP、`.skill` 包或 URL 导入。
- AI 应用可以注册为 RAG 或 Workflow 类型。
- AI 应用会生成 Gateway 可调用的 `call.js`，并同步成技能目录。
- 系统会从 `name + description` 自动提取触发词，最多保留 15 个触发词。

### 4.2 路由机制

用户提问后，MineEcho 会对可用技能打分：

- trigger 完全匹配、前缀匹配、包含匹配。
- skill name 命中。
- description/category 与用户问题 token overlap。
- auto mode 下给启用技能轻量加权。

路由器返回候选 skill、得分和 evidence，因此不是黑箱选择。用户可以看到为什么某个技能或 AI 应用被推荐。

### 4.3 对协同办公的意义

| 场景 | MineEcho 的协同方式 |
|------|---------------------|
| 企业已有 RAG 应用 | 注册为 AI app，转换成 skill，被聊天路由调用 |
| 团队内部工具脚本 | 打包成 skill，进入技能中心和触发词索引 |
| 复杂任务 | 先由路由判断是否需要专用能力，再进入通用聊天或 Gateway 执行 |
| 技能治理 | 健康检查、触发词预览、安全扫描、启用/禁用状态统一管理 |

## 5. TokenJuice：不是简单截断，而是规则化上下文压缩

TokenJuice 当前覆盖 15 类内置规则：

- `git status`、`git diff`、`git log`
- `npm test`、`npm list`
- `cargo build`、`cargo test`
- `docker logs`、`docker ps`
- PDF、DOCX、PPTX、XLSX、HTML 文档抽取
- 通用 fallback

它的策略不是把模型输出强行截断，而是针对不同场景保留关键事实：

- 错误场景保留 exit code、错误摘要、head/tail。
- 测试场景统计 pass/fail/skip。
- git diff 统计 additions/deletions，过滤重复元信息。
- docker logs 统计 error/warn，压缩时间戳噪声。
- 文档抽取去空行、去相邻重复，并保留头尾结构。

### 5.1 Token 节省估算

下面是基于当前规则结构的工程估算，不是公开 benchmark。真实节省比例取决于输出长度、重复程度和错误密度；MineEcho 会在本地记录 raw/reduced 字符数和 estimated tokens saved，可用于后续真实统计。

| 场景 | 常见输入 | 保留内容 | 估算 token 节省 |
|------|----------|----------|----------------|
| `git status` | 分支、变更文件、未跟踪文件说明 | 文件状态摘要 | 40%-70% |
| `git diff` | 大量 diff header、index、空行、长 patch | 头 30 行、尾 10 行、增删统计 | 50%-85% |
| `npm test` / `cargo test` | 长测试日志、堆栈、重复 pass 行 | 头尾、pass/fail/skip 计数、失败上下文 | 30%-75% |
| `docker logs` | 时间戳密集日志、重复服务输出 | 去时间戳噪声、保留头尾、error/warn 计数 | 40%-80% |
| PDF/DOCX/PPTX/XLSX/HTML 抽取 | 空行、重复段落、长文档 | 去空行/重复、头尾摘要、页数/错误计数 | 35%-80% |
| 通用 fallback | 未命中特定规则的大段输出 | head/tail + 中间省略 | 20%-60% |

### 5.2 如何得到真实数据

当前 BFF 会记录 TokenJuice 指标：

- `totalRawChars`
- `totalReducedChars`
- `totalSavedChars`
- `estimatedTokensSaved`
- `averageRatio`
- 按 family / reducer 聚合

如果要发布正式 benchmark，建议用 5 类固定样本各跑 20-50 次，输出公开表格。文档中暂不伪造“实测节省 73%”这类结论。

## 6. 与其他形态产品的定位差异

| 产品形态 | 常见优势 | 常见短板 | MineEcho 的差异点 |
|----------|----------|----------|-------------------|
| 普通 Chat UI | 上手简单 | 不记长期上下文，工具和知识分散 | 加入记忆树、知识库、skill 路由和成本层 |
| 单纯 RAG 知识库 | 能问文档 | 文档碎片化，缺少行动能力 | raw/wiki 双层 + 四通道检索 + AI app/skill 协同 |
| Agent 工具框架 | 能执行工具 | 成本高、上下文噪声大、个人记忆弱 | TokenJuice 控制工具输出，记忆系统长期沉淀 |
| 企业 AI 应用平台 | 应用多 | 应用之间割裂，用户习惯难沉淀 | AI 应用转 skill，统一路由、触发词和健康检查 |
| 纯本地笔记/知识图谱 | 可控、可浏览 | 不会主动调用能力 | 图谱、知识库、记忆和技能进入同一助手链路 |

## 7. 当前边界

为了避免过度承诺，当前版本需要明确这些边界：

- MineEcho 已有后台 Dream Scheduler 和记忆重构入口，但还没有完整的人工审核工作台。
- 长期记忆召回已接入统一 embedding provider 做候选重排，但还没有独立外部向量数据库持久化。
- TokenJuice 已在规则压缩与指标统计层生效，但官方 benchmark 需要后续用固定样本集补充。
- Skill 路由当前以触发词、名称、描述和模式证据为主；高风险执行仍应保留人工确认。

这些边界不削弱当前价值，反而说明 MineEcho 的路线是从“可解释、可验证、可本地运行”的基础能力开始，而不是直接承诺不可控的全自动 Agent。
